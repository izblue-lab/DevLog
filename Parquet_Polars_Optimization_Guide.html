1. 왜 수 GB CSV 파일을 열면 컴퓨터가 멈출까?

기존 데이터 도구(Pandas, Excel)와 행(Row) 기반 CSV 포맷의 구조적 한계와 이를 극복하는 새로운 데이터 패러다임입니다.

⚠️
메모리 폭발(OOM)의 원인: Eager Loading
Pandas의 pd.read_csv()는 파일 전체를 한꺼번에 메모리(RAM)에 로드합니다. 5GB CSV 파일이라도 파이썬 객체로 변환되면 15~20GB의 메모리를 소모하여 16GB 노트북이 즉시 멈추거나 다운됩니다.
비교 항목 기존 방식 (Pandas + CSV) 최적화 방식 (DuckDB/Polars + Parquet)
저장 구조 행(Row) 단위 차곡차곡 저장 열(Column) 단위 묶음 압축 저장
디스크 용량 압축 안 됨 (용량 100% 차지) 강력한 스키마 압축 (최대 70~80% 용량 절감)
데이터 읽기 (I/O) 원하지 않는 모든 열/행을 처음부터 다 읽음 필요한 열과 행 조각만 선택적 스캔 (Pushdown)
메모리 사용량 RAM 용량 초과 시 즉각 크래시 (OOM) 필요한 청크만 올려 노트북에서도 무제한 연산
처리 속도 데이터가 커질수록 급격히 느려짐 기가바이트(GB) 단위도 몇 초 만에 처리

2. Parquet(파케이) 컬럼형 파일 포맷의 마법

엑셀처럼 가로로 저장하지 않고 세로(열)로 저장할 때 일어나는 2대 최적화 원리입니다.

  1. 원리 1 필요한 열만 쏙 골라 읽기 (Projection Pushdown)
    100개의 컬럼(이름, 나이, 주소, 로그인기록 등) 중 '평균 나이'만 구하고 싶을 때, CSV는 100개 컬럼을 디스크에서 전부 읽어야 합니다. 반면 Parquet는 딱 '나이' 열이 들어있는 파일 조각만 읽고 나머지 99개 컬럼은 디스크 I/O를 아예 발생시키지 않습니다.
  2. 원리 2 조건에 안 맞는 데이터 덩어리 통째로 건너뛰기 (Predicate Pushdown)
    Parquet 파일 내부에는 구역마다 메타데이터(최솟값/최댓값 통계)가 들어있습니다. 예를 들어 WHERE 나이 > 30 쿼리를 날리면, DuckDB나 Polars는 메타데이터를 보고 '10대~20대만 모여있는 데이터 블록'은 아예 읽지도 않고 통째로 건너뜁니다.

3. Polars Lazy Scan: 실행하기 전까지는 메모리를 쓰지 않는다

지연 평가(Lazy Evaluation) 쿼리 플래너를 활용하여 파이썬 코드를 최고 효율로 실행하는 방법입니다.

💡
Lazy Scan의 작동 흐름 (3-Step):
1. pl.scan_parquet(): 파일을 메모리에 올리지 않고 구조(스키마)만 파악
2. .filter(), .select(): 어떤 행을 고르고 어떤 열을 남길지 연산 지시서(Query Plan)만 누적
3. .collect(): 엔진이 전체 과정을 분석해 불필요한 연산을 전부 쳐내고 단 1번에 초고속 실행
Python (Polars Lazy Scan 예제) 
import polars as pl

# 1. scan으로 연산 계획(LazyFrame) 생성 (데이터는 아직 메모리에 안 올림)
lazy_query = (
    pl.scan_parquet("large_dataset.parquet")
    .filter(pl.col("age") >= 20)             # Predicate Pushdown (조건 불일치 블록 스킵)
    .select(["name", "age", "payment"])      # Projection Pushdown (필요한 컬럼만 로드)
    .group_by("age")
    .agg(pl.col("payment").mean())
)

# 2. 최적화된 쿼리 플랜 단 한 번에 실행!
df_result = lazy_query.collect()
print(df_result)

4. DuckDB로 CSV를 Parquet로 1초 만에 바꾸고 쿼리하기

복잡한 DB 서버 설치 없이 SQL 한 줄로 변환하고 분석하는 실무 원스톱 명령어입니다.

SQL (DuckDB 단 한 줄 변환 & 조회) 
-- 1. 대용량 CSV 파일을 Parquet 압축 파일로 초고속 변환 (용량 최대 70~80% 즉시 절감)
COPY (SELECT * FROM 'large_data.csv') 
TO 'optimized_data.parquet' (FORMAT 'PARQUET');

-- 2. DB에 테이블을 만들 필요 없이 Parquet 파일에 바로 SQL 쿼리 실행!
SELECT name, age, AVG(payment) 
FROM 'optimized_data.parquet' 
WHERE age >= 20 
GROUP BY name, age;

5. 언제 쓰고 언제 쓰지 말아야 할까? (적용 가이드)

무조건 쓰는 것이 능사가 아닙니다. 데이터 작업의 성격에 맞춰 올바른 스택을 선택하세요.

✅ 이럴 때 무조건 쓰세요 (강력 추천)
  • • 수 GB 이상 공공데이터, 로그, 매출 데이터 분석 시
  • • 내 노트북 RAM 용량을 초과하는 대용량 데이터를 다룰 때
  • • 특정 컬럼/필터 조건 위주로 통계·집계를 낼 때 (OLAP)
  • • 비싼 클라우드 DB 비용 없이 로컬에서 끝내고 싶을 때
❌ 이럴 때는 쓰지 마세요 (비추천)
  • • 실시간으로 댓글이 달리는 등 1줄씩 빈번히 쓰기/수정할 때
  • • 한 사람의 정보를 자주 변경해야 하는 웹 서비스 백엔드 (OLTP)
  • • 10MB 이하의 아주 작은 소규모 엑셀 파일 가공 시
  • • 단순 Key-Value 캐싱이 필요할 때 (Redis 등 권장)

6. 자주 묻는 질문 (FAQ)

실무 적용 시 가장 많이 혼동하는 핵심 질문들을 모았습니다.

데이터의 형태나 중복도에 따라 압축률의 차이는 있지만, Parquet는 컬럼 기반 저장소와 Snappy/ZSTD 압축 알고리즘을 사용해 텍스트 기반 CSV 대비 보통 5배~10배(70~90%) 이상 용량을 획기적으로 줄여줍니다 (예: 50GB CSV ➔ 약 5~10GB 내외).

여기에 DuckDB나 Polars Lazy Scan을 결합하면 전체 데이터를 메모리에 올리지 않고 필요한 열과 조건에 맞는 행만 조각(Vector/Chunk) 단위로 스트리밍 처리하기 때문에, 과거에는 대형 서버 없이는 불가능했던 대용량 데이터 연산도 8GB~16GB 기본 노트북 환경에서 메모리 폭발(OOM) 걱정 없이 충분히 시도하고 처리할 수 있게 됩니다.
네, 아주 간단합니다. pl.from_pandas(df).lazy()를 호출하면 즉시 LazyFrame으로 전환됩니다. 이후 복잡한 필터, 조인, 집계 체이닝을 걸고 마지막에 .collect()를 호출하면 연산 순서를 엔진이 알아서 최적화해 줍니다.
SQL 쿼리가 더 익숙하고 빠른 분석 보고서를 뽑아야 한다면 DuckDB가 유리하며, 파이썬 코드 기반으로 복잡한 머신러닝 전처리나 파이프라인 체이닝을 구성해야 한다면 Polars가 유리합니다. 두 도구 모두 Apache Arrow 메모리 포맷을 공유하므로 서로 데이터를 비용 없이(Zero-Copy) 즉시 주고받을 수 있습니다.
